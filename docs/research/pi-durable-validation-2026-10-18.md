# Pi Durable 原型验证结论

日期：2026-10-18。测试版本：`@earendil-works/pi-durable@1.3.0`。实现位于 [infra/pi-durable-validation](../../infra/pi-durable-validation/README.md)。

> 本文记录第一轮执行机制验证。后续同日已补齐主题侧聊、共享记忆和模型可见的交付，测试覆盖与使用方式见 [最新原型说明](../../infra/pi-durable-validation/README.md)。

## 判断

**Durable 已通过本轮核心执行链路验证，值得继续做个人 Agent 的产品原型。** 主对话、后台工作、恢复和定时模型唤醒可以放在同一套持久运行时中，CLI 可以随时退出。这个结果提供了执行基础的证据，还不足以决定替换 Point 当前选用的 Pi coding-agent SDK。

浏览器按用户要求不参与验证。原型独立于 `server/`，没有修改现有 SDK 实现或正式选型。

## 验证了什么

| 产品行为 | 实际实现 | 观测结果 |
|---|---|---|
| 普通 CLI Agent | 主模型、CodingTools、持久对话 | 真实模型调用 write/read 成功；会话和显式偏好经强杀恢复 |
| 用户离开后继续工作 | 常驻服务拥有任务；CLI 仅提交/订阅 | 提交进程退出后继续完成；主对话仍能响应 |
| 中途补充和停止 | 任务版本、独立子会话、持久取消 | 同一子会话处理新要求；旧答复不发布；停止主对话不误杀后台工作 |
| 进程恢复 | Durable task/checkpoint + SQLite | 相同任务及子会话继续，最终结果不重复回报 |
| 主动跟进 | 持久时间点唤醒专属模型会话 | 停机错过的跟进补执行；改期淘汰旧计划；取消和已完成状态跨重启保留 |
| 结果主动展示 | 原子写入主对话条目 + SSE | CLI 无需再次提问即可显示完成及模型生成的跟进；重连能读取当前状态 |
| 外部动作边界 | 独立接收端、投递意图、稳定幂等键 | 有幂等契约时重发不重复生效；无契约时标 unknown 并停止自动重发 |
| 工具与网络失败 | 工具回执校验、未知投递状态 | 模型单凭文本不能把工具失败包装为成功；网络失败不伪造成功 |

“中途补充”在当前模型轮完成后生效，不承诺即时打断改写；“主动跟进”是用户明确设置的一次计划，没有验证自主决定何时联系用户。

## 证据

完整套件 **13/13 通过**，耗时约 24 秒。五个关键故障点各 10 轮，共 50 次强杀：

| 故障窗口 | 轮数 | 核对项 |
|---|---:|---|
| 工具已写文件、尚未保存回执 | 10 | 同一任务恢复，确定性文件可重复覆盖，报告只回报一次 |
| 模型已回答、尚未提交业务结果 | 10 | 恢复同一子会话，不创建第二个业务任务 |
| 报告已写文件、尚未提交阶段 | 10 | 只有一个最终报告文件和一条回报 |
| 独立接收端已生效、Agent 尚未保存确认 | 10 | 每轮两次请求、一次实际效果 |
| 即将向主对话回报 | 10 | 业务完成、主对话条目、跟进计划原子提交 |

这些故障测试使用脚本模型，真实执行任务运行时、工具、文件、HTTP、SQLite 和 SIGKILL。其他用例另外覆盖提醒、取消及不支持幂等的接收端。证据和接收端账本保存在：

## 对产品设计的意义

可以围绕一条连续体验设计产品：用户交代任务，继续聊天或离开；后台完成后带着产物回来；用户补充要求；系统在约定时间再跟进。Durable 的价值主要体现在这些行为跨会话请求和进程生命周期仍然成立。

业务层仍必须定义什么叫完成、如何处理新要求、取消后留下什么，以及哪些外部动作允许重试。原型约 400 行核心服务代码包含了这些规则；运行时没有替产品作决定。

其中最关键的约束是外部副作用：`requestId` 去重不是通知、支付或其他外部写操作的幂等保证。没有接收端幂等或可查回执的契约，就必须保留“结果未知”这一产品状态，并设计后续核实方式。本原型没有提供人工核销接口。

## 尚不能据此下结论的部分

- Pi 插件生态能否迁移，以及复用 SDK 插件与重写 Durable extension 的实际成本。
- 真实模型流中断、限流、供应商故障后的成本与恢复体验。
- 多任务长期运行、上下文增长、数据库增长和依赖升级迁移。
- Muse 式记忆、主动判断、通知节制与持续使用价值。

**下一阶段应给这个执行核心接一个最薄的产品界面，围绕“交代—离开—回来—纠正—跟进”进行真实使用验证，并另做插件迁移成本对照。** 本轮已经验证了核心运行机制；最终选型应同时考虑产品体验和生态成本。
