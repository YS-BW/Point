# 会话与跟进默认策略

> 更新：2026-10-18。会话采用 Pi Durable，main / 主题侧聊 / 内部执行会话由 Point 组织。既有待办与跟进默认值保留。

## 会话组织

| 类型 | 体验与生命周期 |
|---|---|
| main | 长期主会话，默认入口，保留稳定身份与历史；不因结束某个任务而清空 |
| 主题侧聊 | 同一个助手的另一段持续对话，可短期使用也可长期保留，独立历史，可重命名、归档和恢复 |
| 内部执行会话 | 后台任务的工作上下文，不自动作为新的用户侧聊展示；按任务保存、恢复与停止 |

主题可以 fresh 创建，也可以从现有会话的完整消息边界 fork，保存来源关系。fork 后历史分别发展，不自动持续镜像 main；共享已保存的记忆，活动浏览器句柄不随 fork 继承。

这借用了“主线与分支”的组织直觉，产品不提供 Git 式逐条消息 merge。用户要求同步时，Share task 将主题已确认结论、产物引用、未解决事项整理为带来源的输入交给 main，原主题保留。同步不会自动把暂时探索写成长期偏好。

切换会话不停止后台工作。归档保留历史，不取消已有任务；归档后新结果和跟进路由到 main，已经进入原会话模型队列的消息不承诺搬移。恢复主题沿用同一会话。main 默认保持活跃。

## 后台结果与用户控制

任务回到所属聊天；侧聊任务默认只回侧聊，用户要求 main 摘要或由 main 委派到侧聊时，可同时回 main。其他会话有结果时 Client 可显示未读提示，不强制切换当前对话。

普通输入忙碌时排队，明确补充当前执行时使用 steer 语义。停止当前回答、取消某个后台任务、停止全部工作分别处理；退出 CLI 或关闭 Web 只断开客户端。浏览器人工接管仅阻止对应资源的 Agent 输入，交还后重新观察。

理解与表达主要由提示词/策略负责；持久状态、取消、定时与投递由 Point 通过 Durable task/document 保证。一次跟进原型已实现，完整待办提醒策略仍需产品集成验收。

## 首个验证场景

从直接对话发现承诺与待办，记住状态，必要时准备草稿和提醒。先做好基础对话，不接入其他平台数据源；产品能力不限于此场景。

| 场景 | 已确认行为 |
|---|---|
| 明确承诺，如“周五前给小王发方案” | 自动建立待办并简短告知，可纠正或取消 |
| 模糊意愿，如“有空想看看” | 不自动建立待办 |
| 明确待办但无截止时间 | 先记下，不催促；可查看、补时间或取消 |
| 自然表达明确完成 | 自动更新对应待办并停止提醒；只描述进展则不算完成，有歧义才问 |
| 提醒节奏 | 提前一次；到期仍未确认完成，再追问一次，之后停止自动催促 |
| 提前多久 | 根据工作量判断，在记下时告知用户，可通过对话调整；不是固定提前一天 |
| 模糊日期/时刻 | 采用默认解释并显示具体日期和时间；关键歧义才追问；具体映射规则待定 |
| 草稿准备 | 可利用已有对话主动准备，随提醒提供；实际发送由用户决定 |
| 缺少关键信息 | 完成有依据的部分，标出缺项，在原定提醒时询问，不额外打扰 |
| 明确改期 | 更新待办、撤掉旧提醒，调整正在进行的准备 |
| 明确取消 | 取消待办，停止提醒和准备 |
| “别催了” | 停止提醒与主动准备，保留待办，之后可恢复 |
| “这次不用提醒” | 只跳过当前提醒，后续安排保留 |
| 停机错过提前提醒和到期追问 | 恢复后合并为一次过期跟进，之后停止自动催促；不补发两条旧提醒 |

停止催促不等于任务完成。多个操作指向不明确时澄清，不猜测修改对象。

## 当前不做

- 用户明确暂不考虑免打扰时段；不默认加 23:00–08:00 等规则。
- 通知仅单向投递，不处理邮件回复；状态更新回到对话入口。
- 不把“自动起草”扩张为所有外部动作均可自动提交。更广泛的行动策略未在本轮逐项决定。

## 交付前需要验证的序列

1. 建待办 → 安排准备与提醒 → 对话明确完成 → 所有陈旧提醒不再投递。
2. 草稿准备中改期/取消 → 更新执行安排 → 旧结果不触发错误通知。
3. 无截止待办 → 长期保存 → 不凭空生成催促。
4. 重启时两次提醒均过期 → 合并跟进一次 → 不自动循环催促。
