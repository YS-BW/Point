# 触发、调度与后台工作

> 更新：2026-10-18。持久执行与到期唤醒统一使用 Pi Durable task；Point 定义计划、重复规则、错过处理与通知语义。

## 触发源

| 类型 | 用途 |
|---|---|
| 时间 | 待办提醒、任务准备、周期维护 |
| 对话/状态变化 | 用户改期/取消、任务完成、需要输入 |
| 外部事件 | 后续邮件、社交媒体、网购平台等连接器的数据变化 |
| 自省 | 检查是否有值得推进的工作，允许无动作 |

触发产生待评估工作，不直接等于通知。判断层决定做什么，投递层决定怎样呈现。不预设 15–30 分钟巡检、每小时维护或每日 Digest 为第一版硬要求。

## Durable 承载

Point 在 document 中保存计划与任务/目标关联、启用状态、要求版本、时区、到期时间、最近结果和失败情况；Durable Task/checkpoint 保存运行进度。计划解释与实际执行分别有权威记录，不为同一计划再启一个独立 cron/插件进程重复投递。

- 持久任务用 `runtime.sleep()` 等待已保存的绝对时间；唤醒时重新检查计划状态与版本。恢复不能按“现在 + 间隔”不断顺延原定时间。
- 到期时按稳定运行 ID 创建一次业务执行；要求版本变化或已取消的旧运行跳过，投递前再核对。
- 单次跟进沿用原型 Followup task；周期计划需显式定义时区、下一次时间、重叠运行与补跑策略，仍待实现。
- 外部事件先持久化并去重，再触发工作；对话输入、事件和通知可以关联同一产品任务。
- 网络失败的重试、退避、运行时限与暂停阈值由 Point 配置并持久化，不能假定 runtime 自动完成全部产品重试策略。
- 一个 job 失败不阻塞其他独立工作；浏览器容量、文件冲突和成本预算需单独控制。

Pi 调度插件保留作行为参考或独立逻辑候选。默认不启动 `pi-schedule-prompt` / `pi-scheduler` 作为第二套调度后端，也不依赖其终端会话生命周期。

## 常驻、恢复与错过计划

Docker/supervisor 拉起 Point Server，重开同一 storage 后恢复调度。进程完全停止期间不执行动作；恢复后依据计划与动作记录核对待办、待投递与未知结果。运行时恢复不是外部副作用自动成功。

已确认的提醒规则：停机期间若提前提醒和到期追问均已错过，恢复后合并一次过期跟进，之后停止自动催促，待办不因此完成。其他周期任务分别选跳过、合并或补跑，维护与外部写操作不能一概补齐全部历史触发。

取消、完成、改期使旧计划和陈旧通知失效；改期与新计划创建尽量原子提交。已进入模型处理的输入、已发送消息或外部动作无法靠删除计划撤销。

可注入时钟/手动驱动用于评测，不要求公开外部 tick HTTP 接口。用户暂不考虑免打扰，不增加默认 quiet hours。

## 长期目标

长期目标由状态、事件与未来检查连接起来。Agent 需要工作时运行，等待时只保存状态；自动继续模型循环不等于时间调度，也不等于目标规划。

原型已验证一次计划、替换/取消与强杀恢复；还需完成周期计划、重叠处理、目标唤醒、停机合并、供应商故障退避和长时间资源回收验收。
