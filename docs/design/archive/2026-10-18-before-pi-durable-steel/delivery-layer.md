# 投递与通知

> **已定：通知是可替换的单向手段；不绑定邮箱，不处理邮件回复。**

## 对话与外部渠道

对话是指令和状态更新入口。后台结果可在对话中展示，适合外部提醒时再经渠道送达。邮件、系统通知、push 都是候选，首个实际渠道尚未决定。

即使某个渠道发送失败，任务结果仍应能在 Client 恢复访问。Client 关闭不停止 Server 工作。

旧方案的“邮箱为主、入站/出站邮箱、回复邮件回 L1”不再适用。第一轮不接入邮箱等外部数据源；若未来读取外部消息，需要另行设计来源与指令身份边界。

## 展示范围

主对话展示结果及必要状态；任务视图展示执行详情；工作区展示产物；浏览器视图提供查看和接手。技术审计不必每条都变成聊天消息或外部推送。

详细决策审计界面后置，但后台需保留解释通知/沉默及投递失败所需的记录。单一逻辑提醒可以同时有对话展示和渠道投递，不因此重复消耗两次跟进次数。

## 渠道契约（草案）

渠道接收稳定的通知 ID、内容、任务引用与时效信息，回报成功、失败、跳过或结果未知；错误需可追踪和按策略重试。具体接口尚未实现。

- 投递前检查任务是否完成、取消、改期，以及内容是否仍有效。
- 浏览器实时连接不等于用户正在注意；网页关闭后的推送是独立能力。
- 发送成功不等于用户已读，不能作为任务完成依据。
- 对同一通知的重试使用渠道支持的幂等能力；本地去重不能保证外部恰好一次。
- 已发送但未保存回执时，结果可能未知；按渠道查询或核对，不盲目假定失败重发。

不沿用 durable `requestId` 作为邮件或 push 不重复的证明。

## 合并与默认策略

按已确认规则处理错过的待办提醒，见 [conversation-and-followup.md](conversation-and-followup.md)。其他候选可合并或延后呈现，具体 Digest 时间、条数与模板尚未决定，不强制发送空汇总。

用户暂不考虑免打扰时段。渠道限流与故障退避是工程问题，独立于免打扰产品功能。

## 传输与前端协议

SDK 事件可适配到 Server 的客户端流。HTTP + SSE 和 AG-UI 均为候选，不直接复用旧 durable AgentEvent 映射表。具体选择等 Server 接口与 Web 实现阶段决定。
