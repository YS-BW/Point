# 对话与跟进默认策略

> 这些是本轮用户确认的交互默认值，不是新的独立子系统。理解与表达主要由提示词/策略负责；持久状态、取消、定时和投递由 Server 保证。

## 首个验证场景

从直接对话发现承诺与待办，记住状态，必要时准备草稿和提醒。先做好基础对话，不接入其他平台数据源；产品能力不限于此场景。

| 场景 | 已确认行为 |
|---|---|
| 明确承诺，如“周五前给小王发方案” | 自动建立待办并简短告知，可纠正或取消 |
| 模糊意愿，如“有空想看看” | 不自动建立待办 |
| 明确待办但无截止时间 | 先记下，不催促；可查看、补时间或取消 |
| 自然表达明确完成 | 自动更新对应待办并停止提醒；只描述进展则不算完成，有歧义才问 |
| 提醒节奏 | 提前一次；到期仍未确认完成，再追问一次，之后停止自动催促 |
| 提前多久 | 根据工作量判断，在记下时告知用户，可通过对话调整；不是固定提前一天 |
| 模糊日期/时刻 | 采用默认解释并显示具体日期和时间；关键歧义才追问；具体映射规则待定 |
| 草稿准备 | 可利用已有对话主动准备，随提醒提供；实际发送由用户决定 |
| 缺少关键信息 | 完成有依据的部分，标出缺项，在原定提醒时询问，不额外打扰 |
| 明确改期 | 更新待办、撤掉旧提醒，调整正在进行的准备 |
| 明确取消 | 取消待办，停止提醒和准备 |
| “别催了” | 停止提醒与主动准备，保留待办，之后可恢复 |
| “这次不用提醒” | 只跳过当前提醒，后续安排保留 |
| 停机错过提前提醒和到期追问 | 恢复后合并为一次过期跟进，之后停止自动催促；不补发两条旧提醒 |

停止催促不等于任务完成。多个操作指向不明确时澄清，不猜测修改对象。

## 当前不做

- 用户明确暂不考虑免打扰时段；不默认加 23:00–08:00 等规则。
- 通知仅单向投递，不处理邮件回复；状态更新回到对话入口。
- 不把“自动起草”扩张为所有外部动作均可自动提交。更广泛的行动策略未在本轮逐项决定。

## 交付前需要验证的序列

1. 建待办 → 安排准备与提醒 → 对话明确完成 → 所有陈旧提醒不再投递。
2. 草稿准备中改期/取消 → 更新执行安排 → 旧结果不触发错误通知。
3. 无截止待办 → 长期保存 → 不凭空生成催促。
4. 重启时两次提醒均过期 → 合并跟进一次 → 不自动循环催促。
