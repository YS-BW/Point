# 触发、调度与后台工作

> 方向已定：Server 常驻，任务独立管理；优先评估 Pi 调度插件。具体插件、周期、存储与重试参数尚未选定。

## 触发源

| 类型 | 用途 |
|---|---|
| 时间 | 待办提醒、任务准备、周期性维护 |
| 对话/状态变化 | 用户改期或取消、任务完成、需要输入 |
| 外部事件 | 以后接入邮件、社交媒体、网购平台等数据源 |
| 自省 | 检查是否有值得推进的工作，允许无动作 |

触发不直接等于通知。它产生待评估的工作或候选，由执行/判断层决定是否处理、由投递层决定如何呈现。

不再把“15–30 分钟巡检、每小时维护、每天 Digest”设为第一版硬要求。对话跟进优先按任务安排；维护与目标检查的节奏按实际能力确定。独立 job 的失败不能阻塞其他工作或主对话。

## 插件复用路线

- `pi-schedule-prompt`：主/后台 prompt、单次/周期/cron 与计划持久化；检查无终端 SDK 生命周期。
- `@fookhsu/pi-scheduler`：独立调度核心与 Agent Adapter；默认 CLI 隔离运行、串行到期任务和自身恢复规则需要与常驻 Server 对齐。
- 其他候选可比较，但不因名字中有 scheduler 就视为满足持久恢复。

链接与已查阅边界见 [runtime-selection.md](runtime-selection.md)。尚未安装或运行候选插件。本轮不预先指定自写调度器。

## 需要统一的状态与契约

每项计划需能关联任务/目标，查看启用状态、下次运行、最近结果和失败情况；每次运行需可追踪。具体字段和唯一键由选定后端确定。

- 一个计划只由一个权威调度后端持有，避免插件和 Point 双重触发。
- 对同次调度去重与对外动作去重分开处理。
- 任务取消、完成、改期后，旧计划和陈旧结果不得继续触发提醒。
- 重试、退避、暂停阈值和运行时限要显式配置；旧文档“失败 5 次”的数值不是当前硬决定。
- 可注入时钟/手动驱动是评测需求；不因此要求公开一个外部 tick HTTP 接口。

## 错过计划与恢复

已确认的提醒规则：若停机期间提前提醒与到期追问都已错过，恢复后合并一次过期跟进，之后停止自动催促，待办不因此完成。

这不代表所有类型的 cron 都要同样补跑。维护、草稿准备、外部动作的过期处理应分别定义。运行中断可标记待核查；恢复会话不是恢复所有工具的成功状态。

用户暂不考虑免打扰；当前不增加 quiet hours 或默认推迟时段。

## 长期目标

Goal 插件的 auto-continue 与时间调度是不同能力：前者维持一段执行，后者在未来唤醒。长期目标在无工作时不必持续占用模型；需把目标状态、事件与未来检查连接起来。具体联动待插件验证。
