# 上下文与记忆

> 主对话是产品入口，内部执行使用多个 Pi SDK session。旧的“底层只有一条会话/事件流”与 durable head/ContextEdit 方案已替换。

## 主对话与任务上下文

主 session 保留与用户持续交互的历史。每个任务的子 session 保存自己的执行上下文，同一任务可以继续，独立任务不混入彼此的全部历史。

委派时传递明确任务、相关上下文、约束与必要引用；不默认复制全部主对话。共享记忆通过同一入口访问，任务结果回传主 Agent 时保留任务和产物关联。

Pi SDK 的 SessionManager 是模型会话历史的权威来源；Point/选定插件管理业务任务、目标和计划。两者用 ID 关联，不再声称所有状态都是一条自建事件流的投影。若需要统一审计时间线，可汇聚业务事件和 session 引用，但不重复接管 SDK 历史。

## 上下文组装方向

- 稳定的人格、用户画像、行为规则以小规模上下文提供。
- 记忆索引保持简洁；详细记忆和历史通过按需工具检索。
- 采用 SDK 现有压缩和上下文机制，不重新实现旧 durable 投影接口。
- 检索结果、工具返回控制体积并标明裁剪，必要时能取原文。
- 用户纠正、任务取消和新截止时间必须及时生效，不能为缓存稳定而保留错误事实。

索引注入 + 工具取详情仍是设计方向。不能笼统承诺“动态注入必然让全部 prompt cache 失效”；缓存表现取决于模型提供方与具体上下文布局，需要实测。

## 记忆质量要求

保留来源引用，区分用户明说、Agent 推断和外部资料；记录事实的时效性与替代关系；用户明确编辑/纠正优先于后台抽取。

长期原文保留有利于回溯，结构化抽取也可能有损。定期回检是候选维护机制，不能保证发现所有漏记。抽取与回检周期待定。

## 删除语义尚未闭合

旧文档同时承诺“原文只增不删”和“删除真删”，两者冲突，不再作为并列保证。

需要区分“以后别用”与“删除原文及派生数据”，确定摘要、索引、缓存、审计、备份的处理范围，以及防止重新抽取的机制。尚未验证前不宣称彻底删除。来源字段应尽早保留，不把将来的可追溯性寄托在无法补回的历史上。

## 待验证

- SDK 历史检索与多任务引用方式、上下文预算。
- 记忆插件能否覆盖来源、编辑优先、时效与删除要求。
- 任务间共享文件/记忆的并发更新与冲突处理。
- 错误记忆的修订、派生画像更新和删除验证范围。

Muse 参考需准确：它有主对话，也有 side chats。Point 选择主入口不代表其内部只能有一个执行会话。
