# 投递层设计（L4）

> 状态：**✅ 已定**
> 结论：**验证阶段用「CLI 决策面板 + 邮箱投递」；投递层从第一行代码就做成可插拔；入站邮箱与出站邮箱分离。**

---

## 1. L4 不是 L2 的被动执行者

先划清边界——**这是两层判断，不是一个**：

| 层 | 回答什么问题 |
|---|---|
| **L2 判断** | 这件事**值不值得说**（四档） |
| **L4 投递** | **现在送到吗 · 送到哪个设备 · 要不要合并 · 用什么渠道** |

L2 说「值得说」，L4 仍可能决定「但现在不送」——比如你在会议中、或前面 5 分钟刚推过一条。

**L4 的主要工作是决定「不送」。**

---

## 2. ★ 两个视图，不是两个界面

这是本轮最重要的设计结论。**验证阶段需要的不是「聊天界面」，是两个职责完全不同的视图：**

| 视图 | 给谁 | 内容 | 特征 |
|---|---|---|---|
| **决策面板** | **你**（调试 / 审计 / 可解释性） | 每条裁决：候选 + 分数 + 五维理由 + 被压下的原因 | 结构化 · 常驻 · 可搜索 · **高频（几十条/天）** |
| **投递渠道** | **你**（作为用户） | 真正值得说出口的那几条 | 克制 · 分档 · 可静音 · **低频（几条/天）** |

**为什么不能只做聊天界面**：聊天只能显示「说了什么」，**显示不了「为什么没说」**——而后者才是本项目的核心差异化。用聊天界面验证，你会验证不了自己最想验证的东西。

**这个分裂还带来一个约束**：两者必须一开始就分开，不能混在一个 UI 里。

---

## 3. 四档到落点的映射

| 档位 | 含义 | 落点 | 渠道 |
|---|---|---|---|
| `SPEAK_NOW` | 现在就值得说 | 即时渠道 | ⚠️ 邮箱延迟不够（见 §6） |
| **`DIGEST`** | 值得说，但不值得现在 | 攒起来，定时汇总 | ✅✅ **邮箱（默认档）** |
| `ACT_THEN_REPORT` | 先做完，做完再说 | 结果通知 | ✅ 邮箱 |
| `SILENT_LOG` | 只记，不说 | 决策面板可回看 | ❌ 不投递 |

**`DIGEST` 是默认档**，依据是 PROACTIVITY-GYM 的真人研究：
> 做对了事但**时机不对，信任断崖式下跌**；用户**宁可要事后/睡眠时段的不完美帮助，也不愿被打断专注**。

**邮箱恰好只适合 DIGEST 档**——这不是巧合，是邮件这种介质的性质决定的（延迟数十秒到数分钟、不适合高频）。

---

## 4. ★ 渠道选型：邮箱为主

### 为什么邮箱（五条）

| 好处 | 说明 |
|---|---|
| **零额外基础设施** | L1 本来就要读邮件（IMAP），**发信是同一套配置**（SMTP） |
| **推送可达性最好** | 手机邮件 app 都开着系统推送，**任何设备都能读** |
| **零成本、无限量** | 自用场景下不花钱 |
| **天然持久 + 可搜索** | 邮件本身就是归档，不用另建存储 |
| **可带 HTML/Markdown** | 能做出比纯文本推送好得多的早报样式 |

### ★ 它是**双向**通道（这点被低估）

```
你 → 邮件 → agent        （L1 的 IMAP 触发源，本来就在读）
agent → 邮件 → 你        （L4 的 SMTP 投递）
```

**用户直接回复邮件 = 免费的回程通道。** 回复天然带引用上下文，不用额外做会话关联。

**对比**：ntfy 是纯单向；Telegram 要额外处理 bot 交互；邮箱的回复是「用户本来就会的动作」。

### 邮箱的三个限制

| 限制 | 影响 |
|---|---|
| **延迟数十秒—分钟** | ❌ 不适合 `SPEAK_NOW`；✅ 适合 `DIGEST` |
| **没有可靠的已读信号** | read receipt 不可信 → **L2 的「打断代价」特征不能靠邮件拿**（得靠用户是否回复、或其他渠道的在线状态） |
| **不适合高频** | 决策面板**绝不能**走邮件（几十条/天 = 骚扰） |

## 5. ★ 入站与出站必须分离（两种邮箱）

**这是本轮第二个重要结论。**

| 用途 | 用什么 | 为什么 |
|---|---|---|
| **入站**：agent 读你的邮件（上下文来源 / L1 触发） | **你的真实邮箱**（只读 OAuth） | agent 专属邮箱里**没有你的邮件** |
| **出站**：agent 给你发通知（L4 投递） | **agent 专属邮箱** | **凭据隔离** + 独立身份 |

### 为什么出站要用 agent 专属邮箱（三条硬理由）

**① 凭据隔离 —— 决定性的一条**

如果用你自己的 Gmail/QQ 发信，agent 就拿到了你个人邮箱的 SMTP 凭据；而 **SMTP 凭据通常同时能读**（IMAP 用同一账号凭据）。

> **等于把全部邮件历史、所有网站的验证邮件、私人通信，一起交给了 agent。**

用 agent 专属邮箱，它只有那个箱子的权限。**这正是我们 L5 定的「凭据隔离」原则在 L4 的落地。**

**② 独立身份**

发件人是 `point@agent.qq.com` 而不是你的地址 → 一眼分辨「这是 agent 发的」，而且**可以按发件人建规则**（自动归档、加标签、单独铃声）。

**③ 送达更干净**

服务商处理 SPF/DKIM/DMARC；「发件人与收件人是两个不同域名」比「自己发给自己」更符合正常邮件流。

> 注：**自用场景下「自建 SMTP 进垃圾箱」那个大坑不存在**——那是发信给别人的问题。用服务商发给你自己，送达没问题。这是自用与产品化的根本区别。

### 「Agent 专属邮箱」品类（2026-10 实查）

| | **AgentMail**（agentmail.to） | **腾讯 Agent Mail**（agent.qq.com） | gork.email |
|---|---|---|---|
| 定位 | "Email inboxes for AI agents"（**YC 背书，$6M seed**） | "**QQ 邮箱为 Agent 打造的专属邮箱**" | Python SDK |
| 免费额度 | ✅ **3 inbox / 3000 封月 / 3GB** | 未确认 | 未确认 |
| 付费 | $20/mo（10 inbox / 1 万封 / 10 域名） | 未确认 | 未确认 |
| 接口 | Python/TS SDK + cURL + CLI + **MCP** | CLI（`agently-cli` v1.0.18，Apache-2.0） | Python SDK |
| **生态对接** | ⭐ **明确列了 Claude Code / Hermes / OpenClaw / Codex / Cursor / Grok** | ⚠️ **本 session 已装 skill，可立即试** | — |
| 附加能力 | 语义搜索 · 数据抽取 · 实时事件 · 自定义域名 · AgentHub · **AgentID**（给 agent 的登录按钮） | OAuth + 中文 | — |

**判断**：AgentMail 的定位最准（明确为 agent harness 做）；腾讯那个国内可用性最好。

### 第三个选项：自有域名

| | 做法 | 评价 |
|---|---|---|
| **自有域名邮箱** | 域名（~¥50/年）+ Cloudflare Email Routing（免费收）+ Resend/自建发信 | **完全自有、可迁移、不绑服务商**，对「完全开源可自托管」的叙事最对味；但配置要半天，SPF/DKIM 要配对 |

## 6. 落地路径：三步走

```
第 1 步（验证阶段）  用你自己的邮箱发给自己
                    零成本、零配置、当天能跑。此时凭据隔离无所谓
                            ↓
第 2 步（长期跑）   换成 agent 专属邮箱
                    腾讯那个现成可用；或 AgentMail 免费额度够个人用
                            ↓
第 3 步（可选）     自有域名
                    如果要做成给别人也能部署的开源项目，这个最干净
```

**切换成本 ≈ 0**，因为投递层从一开始就是可插拔的（见 §7）。

## 7. 投递层接口约束（可插拔）

**唯一的硬约束：渠道必须可替换。** 否则第 2/3 步切换要改核心。

```
deliver(channel, message, decision) → Outcome
```

要求：
1. **渠道实现不感知 L2**——只收到「已决定要送的内容 + 档位」
2. **返回投递结果**（成功 / 失败 / 去重跳过），供 L6 反馈使用
3. **幂等**——同一条裁决重投不产生重复（参考 pi-durable 的 `requestId` 幂等原语）
4. **失败要退避**——连续失败到阈值就自己停（参考 openmuse 的「连续失败 5 次自动 paused」）

**渠道清单（按落地顺序）**：

| 渠道 | 用途 | 依赖 |
|---|---|---|
| `ConsoleChannel` | **零配置**，验证骨架 | 无 |
| `FileChannel`（JSONL） | **决策面板**，不是投递 | 无 |
| `SelfEmailChannel` | 第 1 步 | SMTP 凭据 |
| `AgentMailChannel` | 第 2 步 | AgentMail / agently-cli |
| `PushChannel`（Telegram / ntfy） | 未来 `SPEAK_NOW` 用 | bot token |

## 8. 在线状态（L2 的承重前置）

**L2 的「打断代价」特征依赖它**——没有在线状态，五维里少一维，判断层就是空转。

| 问题 | 本设计下的答案 |
|---|---|
| 怎么知道你在不在线？ | ⚠️ **邮箱给不了**。验证阶段先用**时间规则**（勿扰时段）代理 |
| 什么时候需要真的在线状态？ | 当你要做 `SPEAK_NOW` 的即时推送时（那时有了即时渠道，就有连接状态） |
| 现在能做的替代 | ① 勿扰时段（你有作息）② 「最近是否回复过」作为代理信号 ③ 决策面板里记录「本可打扰但选择攒着」 |

**结论**：验证阶段用**勿扰时段**代替在线状态，**不阻塞**。等有即时渠道时再补。

## 9. Digest 的调度与合并

`DIGEST` 是默认档，所以它是**最高频的出口**，必须设计好：

| 要素 | 决策 |
|---|---|
| **触发时机** | 每日固定时间（如 08:00 / 18:00）——先做两个点 |
| **合并规则** | 同一来源的连续候选合并；语义相近的合并；按 salience 降序排列 |
| **上限** | 单封 Digest 有条数上限（避免变成列表垃圾），超出的降级到只记不说 |
| **空 Digest** | **不发**。「今天没有什么值得说的」本身不该占一封邮件 |
| **可回复** | 每一条都能单独回复 → 走回程通道进 L1 |

**依据**：Muse 的 `feed pulse` 是每小时（00–23），但**用户可见的出口极少**；nanoMuse 的 `feed` 是每天早晨一份。**「攒起来一次说」是这类产品的共同形态。**

## 10. 与 pi-durable 的对接点（已核实的原语）

| 需要 | pi-durable 给的 |
|---|---|
| **系统主动发出告知，但不进模型上下文** | ✅ `type: "write"` submission —— **立即落盘、立即 done，即使 busy 也不排队**（`submissions.ts:189-197`） |
| **投递失败重试不重复** | ✅ `requestId` 幂等 |
| **决策面板的持久化** | ✅ 自定义 entry kind（写进 transcript，可回看可审计） |
| **实时观察** | ✅ `viewState()` / `watchEvents()`（⚠️ 但缓冲上限 100 帧，**投递不能依赖 watch**） |
| ⚠️ 不可依赖 | **不能靠 watch 做投递** —— `spec.md:5285-5289`：溢出时中间态被替换 → 必须把事实持久化成 entry 再扫历史 |

## 11. AG-UI：后续引入，现在不引

**决策（2026-10-16）：现在不引入 [AG-UI](https://docs.ag-ui.com/concepts/events)（CopilotKit 的 Agent-User Interaction Protocol），前端阶段再接。**

`@ag-ui/core` 1.0.3 · **MIT** · **零依赖**（只是一组 TS 类型 + 运行时 schema）。

### 它是什么

**agent ↔ 前端的传输协议**——31 个事件类型，全部关于**一次 run 进行中的实时流**：

| 类别 | 事件 |
|---|---|
| Lifecycle | `RUN_STARTED/FINISHED/ERROR` · `STEP_STARTED/FINISHED` |
| Text | `TEXT_MESSAGE_START/CONTENT/END/CHUNK` |
| Tool | `TOOL_CALL_START/ARGS/END/CHUNK/RESULT` |
| State | `STATE_SNAPSHOT` · `STATE_DELTA` · `MESSAGES_SNAPSHOT` |
| Reasoning | `REASONING_START/MESSAGE_*/END` |
| Subagent | `SUBAGENT_STARTED/FINISHED/ERROR` |
| Activity | `ACTIVITY_SNAPSHOT/DELTA` |
| Special | `RAW` · `CUSTOM` |

### 为什么现在不引

| # | 理由 |
|---|---|
| 1 | **它解决的不是我们现在的问题**——我们现在没有前端 |
| 2 | **和事件流 schema 不重叠、不冲突**——它是**传输层**（run 进行中推给前端），我们要的是**持久层**（一切发生过的，含沉默，跨 run）。不存在「错过就晚」的风险 |
| 3 | **后引入成本极低**——零依赖 + 纯类型定义，且 durable 已有可映射的事件源 |

### ★ 关键发现：durable 已经是「近似 AG-UI」

durable 的 `watchEvents()` 有 **22 种 `AgentEvent`**，和 AG-UI 是同一层，映射近乎 1:1：

| durable AgentEvent | AG-UI Event |
|---|---|
| `run_start` / `run_end` | `RUN_STARTED` / `RUN_FINISHED` |
| `turn_start` / `turn_end` | `STEP_STARTED` / `STEP_FINISHED` |
| `message_start` / `message_update` / `message_end` | `TEXT_MESSAGE_START/CONTENT/END` |
| `tool_execution_start/update/end` | `TOOL_CALL_START/ARGS/END` |
| `viewState()`（Chord 快照） | `STATE_SNAPSHOT` |
| `watch()`（Chord ops） | `STATE_DELTA` |
| 子会话（owned conversation） | `SUBAGENT_*` |

→ **前端阶段的工作是「写一层 durable AgentEvent → AG-UI Event 适配器」，不是重写。**

### ★ AG-UI 覆盖不到的五件事（正是 Point 的差异化）

`trigger` · `candidate` · **`decision`（含「决定不说」）** · `delivery` · `feedback`

**这五个事件类型是 AG-UI 没有的，而它们恰好是我们要自己定的事件流 schema 的核心内容。**

### 两层结构

```
durable AgentEvent ──适配器──► AG-UI Event ──► 前端      （实时流）
        ↑
    （已有，22 种）

我们的事件流（持久）──投影──► 决策面板 / Feed / 审计      （历史与审计）
```

**实时流走 AG-UI，历史与审计走我们自己的 schema。**
