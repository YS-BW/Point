# 上下文与记忆设计

> 状态：**✅ 已定**
> **核心决策：Point 是单会话。优化重心放在「上下文」和「记忆」两层，而不是会话管理。**
> 结论先行：**不设计「会话」，设计「事件流 + 任务 + 记忆」。**

## 0. 为什么单会话

三条证据表明这是这个品类的正确形态：

| 证据 | 出处 |
|---|---|
| "Muse 不是回合制的聊天，而是**一段长对话**" | Meta 设计手记 |
| 「**主对话** can never be deleted」（单数、不可删） | Muse 自身隐私文档 |
| "talking to it works just like **messaging another person**" | Meta 官方公告 |

而 OpenAI dot 的 UI 里**根本没有会话列表**——它的组织维度是 **In progress / Scheduled / Completed**（任务状态）。

→ **用户面对的不是会话，是一条连续的流 + 一堆事的状态。**「新开一个对话」这个动作在 personal agent 里本来就不该存在。

### 但「边界」没消失，只是降级为内部概念

| 职责 | 传统 chat app | Point |
|---|---|---|
| 执行单元 | 一次对话 | **一次 run / turn**（可中断、可 checkpoint、可重试） |
| 隔离单元 | 对话之间不串 | **并发任务不串上下文**；taint 按单元隔离 |
| 授权单元 | — | grant 绑定执行单元（nanoMuse 的「本对话」作用域） |
| 成本单元 | — | 每次执行分配不同上下文预算 |

### ★ 存储推论

| | 传统 | Point |
|---|---|---|
| 底层 | `conversations` → `messages` | **一条 append-only 的事件流**（消息、工具调用、结果、决策，统一按时间排） |
| 组织 | 会话列表 | **Goals（长期）+ Tasks（执行单元）** |
| 上下文窗口 | 「这个会话的历史」 | **从事件流里按相关性取最近 N 条** |

**事件流是唯一真相来源；任务、窗口、记忆、决策都只是它的视图。**
「会话」退化为一个策略参数——「这次取多少历史」——而不是一个数据结构。

## 2. 上下文优化（6 条）

| # | 措施 | 借鉴 / 对立 |
|---|---|---|
| 1 | **事件流为底，窗口只是视图** | 对立 openmuse（外包给 Intelligence） |
| 2 | **窗口裁剪对齐工具交换边界**，并给孤儿调用补结果 | 学 nanoMuse（`never starting inside a tool exchange`） |
| 3 | **磁盘留全量，内存只裁窗口** | 学 OpenClaw（`*.jsonl` 完整，内存裁剪） |
| 4 | **给 agent 一个查历史的工具**（自由文本搜全历史） | 学 Muse 的 `context_fetch` |
| 5 | **裁剪时机对齐 prompt cache TTL** | 学 OpenClaw（`cache-ttl.ts`）——在缓存失效时才裁，省钱 |
| 6 | **工具结果裁剪 + `truncated` 标记** | openmuse 已有（`clipCalendarText`） |

**一条关键区分（决定了整个优化方向）：**

> **别做「摘要式压缩」，做「结构化抽取 + 可检索」。**

| | 摘要式压缩 | 结构化抽取 + 检索 |
|---|---|---|
| 结果 | 一段模糊的旧对话梗概 | 具体事实条目 |
| 可纠错 | ❌ 摘要错了没法改 | ✅ 改那一条 |
| 可解释 | ❌ | ✅ 能追来源 |
| 成本 | 每次超窗都要重压 | 定时批处理 |

**摘要是有损且不可逆的；结构化记忆是可编辑、可审计、可追溯的。**

## 3. 记忆优化（7 条）

对标的都是**别人做错的地方**——这是 Point 的免费差异化。

| # | 措施 | 对立的反面案例 |
|---|---|---|
| 1 | **每条记忆带 provenance**（指向来源消息 id） | Muse 没有；nanoMuse 只在 roadmap 里 |
| 2 | **区分「用户明说」vs「系统推断」** | Muse 的 Instagram skill 被**明确指示不要区分** |
| 3 | **删除真删 + 可校验** | Muse 的 forget **只改笔记、保留 transcript** |
| 4 | **用户改过的行是权威**，后台 job 不得覆盖 | Muse 每小时 job 会重写记忆 |
| 5 | **时效性**：`valid_from` / `valid_until` / `superseded_by` | 所有产品都没有 |
| 6 | **定期回检**：用原文复查有没有漏记 | 所有产品都没有 |
| 7 | **所有数据出口（含 embedding）走同一套 egress 策略** | nanoMuse 自承 embedding 调用**落在 taint 规则之外**——它的策略有洞。**正解是补洞，不是把 embedding 搬到本地** |

### 第 6 条是最重要的，也是最没人做的

它解决的是**「沉默丢失」**：

```
窗口丢失   → 有声：你知道窗口只有 N 条，磁盘上有全量 ✅
抽取丢失   → 无声：某句话被判断"不值得记"，于是消失
               你不知道它漏了，agent 也不知道 ❌
```

**这和 L2 决策层的沉默是同一个病**：

| | 判断什么 | 判断错了 |
|---|---|---|
| L2 决策层 | 什么值得**说** | 漏报——不知道它为什么没说 |
| 记忆层 | 什么值得**记** | 漏记——不知道它为什么没记 |

**同一种药：保留原始 + 审计 + 可追溯。**

## 4. ★ 记忆如何进入上下文：注入 vs 工具

**这是一个必须显式决定的分岔**——它决定记忆层的输出怎么进模型。

### 4.1 判断标准（一句话）

> **如果「模型不知道它」会导致回答明显变差 → 注入。**
> **如果需要的时候才需要 → 做成工具。**

### 4.2 实证：OpenViking 的三级结构就是答案本身

[OpenViking](memory-adapter.md) 的记忆存储是一棵 **Markdown 文件树，三级渐进披露**：

```
├── .abstract.md           # L0: quick relevance check
├── .overview.md           # L1: structure and key points
    ├── .abstract.md
    ├── .overview.md
        ├── auth.md         # L2: full content, loaded on demand
        └── endpoints.md
```

| 层级 | 内容 | 该注入还是该做成工具 |
|---|---|---|
| **L0** `.abstract.md` | 快速相关性检查 | **注入**（极小、每轮都要） |
| **L1** `.overview.md` | 结构和要点 | **注入**（小、稳定） |
| **L2** 全文 | 完整内容 | **工具**（大、按需加载） |

**它摸到了同一个答案。**

### 4.3 ★ 决定性理由：prompt cache

**这是工程上的硬约束，不是偏好。**

pi-durable 的提示词组装**只把与模型已看过内容的差异写成 `pi.system` entry**——内容不变就不重发，**provider 的 prompt cache 就保住了**（这也是「约 40% 更少 prompt token」的来源）。

> **所以注入的内容必须「稳定」。**
> **如果每轮把「检索到的记忆」注入进去，内容每次都变 → system prompt 每次都变 → prompt cache 全废。**

| 注入什么 | 稳定性 | cache 影响 |
|---|---|---|
| 人格 | 几乎不变 | ✅ 无影响 |
| 用户画像 | 慢变（天/周） | ✅ 可接受 |
| 记忆**索引** | 慢变 | ✅ 可接受 |
| **检索结果** | **每轮都变** | ❌ **废掉 cache** |

**这是把「检索结果做成工具」的决定性理由**——不只是省 token，是**保住 cache**。

### 4.4 还有两个理由偏向「工具」

**① 可审计**

工具式能记录「**模型查了什么**」；注入式只记录「注入了什么」。

> 我们的「可解释的沉默」（L2）需要前者。而且工具调用天然是 durable 的 `ToolTask`——自带 replay 策略、可恢复、有 usage 记账。

**② 避开已记录的反模式**

nanoMuse 把**每条 memory 都进 system prompt**（[对标表](#1-对标表) 里的反面案例）——上下文爆炸 + 噪声 + 成本随记忆量线性增长。

### 4.5 三段式上下文

```
① 系统提示词（注入 · 每轮都在 · 稳定）
   ├── 人格            ← section("persona")
   ├── 用户画像        ← L3 Persona / USER.md（小）
   └── 记忆索引        ← .abstract.md 级目录（小）

② 对话上下文（durable 的 head / ContextEdit 管）
   └── 事件流投影

③ 按需（工具 · 模型自己调）
   ├── memory_search / memory_get   ← 具体记忆条目（L1/L2）
   └── context_fetch                ← 历史原文
```

**这正是 Muse 的做法**：`MEMORY.md` / `USER.md` / `SOUL.md` / `IDENTITY.md` 常驻 + `memory_search` / `memory_get` / `context_fetch` 三个工具。

### 4.6 在 pi-durable 里的落点

| 想要 | 怎么做 |
|---|---|
| 注入人格 | `section("persona", () => ...)` |
| 注入用户画像 | `section("user", () => adapter.profile())`（每次请求重渲染，但内容稳定所以 cache 不失效） |
| 注入记忆索引 | 同上，**只注入目录级**（`.abstract.md`） |
| 按需取记忆 | `defineTool` 一个 `memory_search` |
| 按需取历史原文 | `defineTool` 一个 `context_fetch` |
| 上下文投影 | durable 的 `head` / `ContextEdit` |
| **❌ 不要** | 外挂记忆框架的 **takeover**（会和 `head`/`ContextEdit` 打架） |

### 4.7 结论

**采用「注入索引 + 工具取详情」，而不是「注入检索结果」。**

理由排序：
1. **Prompt cache**（技术硬约束）
2. **可审计**（符合「可解释的沉默」）
3. **避开 nanoMuse 的全量注入反模式**

## 5. 两条核心原则

### 原则一：记忆可以有损，原文不能有损

```
   记忆（模糊、结构化、可编辑、带来源）
        ↕ 双向可追溯
   原文（精确、全量、只增不删、可全文检索）
```

**只要原文还在，下游任何丢失都是可修的。所以要保护的不是「上下文」，是原文。**

### 原则二：记忆必须永远能指回原文

第 2 条一旦破了，「有损」就变成了「失真」——你会重演 Muse 的 forget bug：**记忆和原文不一致，而用户不知道。**

**这正好证明：危险的不是「丢失」，是「丢失不可发现」。** Muse 反着犯了个镜像错误——它没丢原文，却制造了「记忆与原文不一致且不可发现」。

## 6. 判断标准（自检）

> **「如果我丢了一条重要信息，多久能发现？」**
>
> - 答「用户下次问起时才发现」→ ❌ 设计有问题
> - 答「夜间回检时会报出来」→ ✅ 设计对了

这条标准和 L2 决策层的「能不能回答为什么没说」是**同一个标准**。

---

## 7. 一个认知校准

**有损不是架构缺陷，是有限工作记忆的本质。** 人脑也是「有损 + 重构式」的，而且有虚构记忆（confabulation），比 LLM 幻觉更严重。

目标不是「完整」，是**连续**：

| 需要 | 不需要 |
|---|---|
| 记得你偏好燕麦奶 | 记得你周二 3 点点了杯咖啡 |
| 记得你答应过某人的事 | 记得那句话的完整措辞 |
| 记得任务做到哪了 | 记得每次工具调用的输出 |

**「personal」的来源是连续性，不是完整性。**

**但有个不对称**：人脑没有可查的原文，**Point 有**。所以 Point 能做到人做不到的事——**记忆是模糊的，但随时能回溯到精确原文。**
