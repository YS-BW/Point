# 触发器与定时任务设计

> 状态：**✅ 已定**
> 结论：**多个独立 job，不是一个 `while True`。起步 3 个，不照抄 Muse 的 24 个。**

## 0. 先破除一个误解

「24 个每日 cron」不是 24 种主动打扰，**恰恰相反**。

| Muse 的 job | 干什么 | 产出消息吗 |
|---|---|---|
| feed pulse（每小时 00–23） | 生成「今天有什么」 | ✅ **这是主动出口** |
| memory extraction（每小时） | 从对话抽取持久事实 | ❌ 静默维护 |
| Relationships（每小时） | 更新人物档案 | ❌ 静默维护 |
| self_improvement（夜间） | 复盘「什么有效、什么崩了」 | ❌ 静默维护 |
| 各连接器同步 | 拉邮件/日历/… | ❌ 静默维护 |

> **大量静默维护，才让少数几个出口变得有价值。**
> 这也解释了为什么「每天几十次后台 turn」和「很少的 push」是配套设计——如果每次 turn 都 push，就是每天 70+ 次推送。

## 1. 核心决策：为什么分成多个独立 job

### ① 节奏由「数据的自然更新频率」决定，不是由「你想多久看一次」决定

| 数据 | 自然节奏 | 所以 job 周期 |
|---|---|---|
| 对话里的新事实 | 对话产生时 | 每小时抽取 |
| 人物关系 | 很慢 | 每小时 |
| 邮件 | 随时 | 轮询或推送 |
| 每日回顾 | 一天一次 | 夜间 |
| 复盘自己 | 需要安静、不打扰 | 夜间 |

**塞进同一个循环，你只能用最保守的周期，或者全都用一个周期。**

### ② 隔离失败 ← 有血淋淋的反面教材

nanoMuse 的做法（审计实测 `nanomuse/server/service.py:1919-1954`）：

```python
while True:
    # 8 件不相关的活串行跑
    ...
    except Exception:
        sleep(30)      # ← 唯一错误处理
```

后果（审计结论原文：**「没有 job queue / per-job next-run / 退避 / 可观测性」**）：
- 第 3 件事抛异常 → **后面 5 件全不跑**
- 用户打字阻塞后台任务
- 记忆整理独占一个 tick
- 一个 tick 只推一个目标
- 最长 30 秒轮询

**Muse 分成独立 job 正是为了避免这个。一个坏了，其他照跑。**

### ③ 可观测性

独立 job 各自有 `last_run` / `next_run` / 成功失败计数 → **能看见**「Relationships job 停了三天」。

塞在一个 `while True` 里，你什么都看不见。

### ④ 成本分层

| job | 能力需求 |
|---|---|
| feed pulse（生成内容） | 中—强 |
| memory extraction（抽取） | 中 |
| 连接器同步（纯 IO） | **不需要模型** |
| 自省巡检 | 弱 |

**独立 job 才能给每个 job 配不同的模型和预算。**

### ⑤ 幂等与并发

每个 job 有自己的 dedup key 和锁 → 可独立重跑、独立暂停、互不干扰。

## 2. 但一半原因是「现实约束」，不是优雅设计

**很多 cron 之所以是 cron，是因为那个数据源没有更好的触发方式。**

| 如果有 push | 就该用事件触发 |
|---|---|
| 邮件到达 | IMAP IDLE / Gmail push |
| 日历变更 | CalDAV push |
| 文件变化 | inotify |

准确表述：

> **24 个 cron = 少数真正需要定时的（日报、夜间复盘）+ 一堆「因为没有 push 只能轮询」的。**

## 3. 触发有四类（定时只是一类）

| 类型 | 例 | 说明 |
|---|---|---|
| **时间** | cron / reminder | 兜底，不是主力 |
| **事件** | 邮件到达、日历临近、文件变化、webhook | 有 push 就用 |
| **状态变化** | 任务完成、设备上线 | |
| **自省** | 周期性 turn，让模型自己看看有什么 | 最像「agent」的一类；产出绝大多数是「没有」 |

**设计约束**：触发源必须**可插拔**（每个来源一个 adapter）。因为「定时」只能覆盖你想得到要检查的东西。

## 4. MVP：起步 3 个 job

| job | 周期 | 干什么 | 产出消息 |
|---|---|---|---|
| **巡检** | 15–30 分钟 | 看有没有新候选 → 有就唤起 agent | ❌（交给 L2） |
| **维护** | 每小时 | 记忆抽取 + 连接器同步 | ❌ |
| **汇总** | 每天固定时间 | Digest + 日报 | ✅ |

**覆盖三件事：醒来 / 记住 / 汇报。** 其他的等有具体需求再加。

## 5. Job 定义（接口草案）

```
Job {
  id
  kind:        巡检 | 维护 | 汇总
  cadence:     周期 / cron 表达式
  next_run_at            ← 可观测、可手动触发
  last_run_at
  last_status: ok | failed
  failure_streak         ← 失败退避的依据
  on_failure:  retry_backoff | pause_after(N)
  model:      哪一档模型（成本分层）
  enabled
}
```

**必备的可观测字段**：`next_run_at` / `last_run_at` / `failure_streak`。

**失败退避**（借 openmuse 的做法）：连续失败 **5 次自动 paused** + 发一条通知——否则一个坏掉的源会持续骚扰你。

**幂等**（借 nanoMuse 的做法）：每个 job 的每次执行有唯一 key，`fired(job_id, key)` 复合主键 → 同一次执行永不重复。

## 6. 时间可被外部推进（为评测预留）

调度器要暴露一个**外部 tick 接口**（借 nanoMuse 的 `POST /api/tick`）：

- 它原本是为了解决「移动端后台被杀」（Android 精确闹钟主动调它）
- 但对 Point 更重要：**它让 Replay Harness 能加速时间**

> 没有这个接口，你的评测就跑不了「模拟一天」。

## 7. 设计原则（一句话）

> **job 的数量应该跟着「数据源的数量」增长，不跟着「你想让它多主动」增长。**

Muse 有 24 个是因为它有 62 个 skills 和一堆连接器要同步——**那是广度带来的，不是主动性的要求。**

**反过来说也成立：如果 job 数在涨但主动性没变好，说明你在加维护，不在加能力。**
