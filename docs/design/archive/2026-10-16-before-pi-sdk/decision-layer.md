# 决策层设计

> 状态：**✅ 已定**
> 结论：**决策层是一个「可替换的 policy」，不是一个「写死的算法」，也不绑定任何具体模型。判断本身交给决策模型；你的工作是特征、审计、评测。**

## 1. 定位：决策层不是一个点

判断发生在三个检查点，**职责不同**：

| 检查点 | 判断什么 | MVP |
|---|---|---|
| **前置**（triage） | 这件事值不值得让 agent 花资源处理？ | ⚠️ 可后置。**但成本会咬你**——L3 执行是贵的那层（强模型 + 工具 + 浏览器） |
| **中置**（ask） | 干到一半，需不需要你输入？ | ⚠️ 长任务才需要 |
| **后置**（surface） | 做完了，这个结果值不值得告诉你？ | ✅ **先做这个** |

> Muse 的官方表述也是后置：*「**完成后**评估结果是否值得 surface」*。

## 2. 决策层是 policy，不是 model

```
判断层接口（唯一契约）
   ├── RulePolicy        ← 显式规则（安全类一律升级，见 §7）
   ├── HeuristicPolicy   ← 显式权重的线性打分（零依赖、确定性）
   └── ModelPolicy       ← 决策模型（本地或云端，可替换）
```

**三层都输出同构结果**，否则无法做 A/B——而 **A/B 是唯一能证明「指标变好了」的方式**。

**「可替换」不是为了防厂商锁定**（决策模型已有多个提供方，锁定不成立），而是为了：
1. **可回归**——确定性实现才能进 CI
2. **可对比**——没有基线就不知道决策模型贡献了多少
3. **可降级**——决策层在关键路径上，挂了会导致行为静默变错

## 3. 决策的输出

```
Decision {
  tier:    SPEAK_NOW | DIGEST | ACT_THEN_REPORT | SILENT_LOG
  score:   0..1
  reasons: [ {dimension, value, weight} ]      ← 可解释
  basis:   规则 / 启发式 / 模型(含版本)          ← 可追溯
}
```

**四档而不是二分类**：

| 档位 | 含义 | 落点 |
|---|---|---|
| `SPEAK_NOW` | 现在就值得说 | push |
| **`DIGEST`** | 值得说，但不值得现在 | 攒着，定时汇总 ← **默认档** |
| `ACT_THEN_REPORT` | 先做完，做完再说 | 结果通知 |
| `SILENT_LOG` | 只记，不说 | Feed 可回看 ← **应是最高频结果** |

**为什么默认档是 DIGEST**——PROACTIVITY-GYM 的 30 人真人研究：
> 做对了事但**时机不对，信任断崖式下跌**；用户**宁可要事后/睡眠时段的不完美帮助，也不愿被打断专注**。

## 4. 判断交给决策模型 —— 品类已经成熟

「决策模型」是一个**有多个提供方的品类**，而且和生成模型在结构上不同：

| | 生成模型 | 决策模型 |
|---|---|---|
| 解码 | 逐 token 自回归 | **非自回归，一次前向出结构化结果** |
| 计费 | input + **output** | **只算 input**（无 output 费用） |
| 量级 | 高 | **低一到两个数量级** |
| 延迟 | 秒级 | **一次前向** |
| 确定性 | 采样 → 不确定 | **固定输入 → 固定输出**（可做 CI 回归） |
| 输出形状 | 文本，要解析 | **带概率的结构化答案**（predicate / choice / score） |
| 能力需求 | 强 | **弱**（判断相关性，不需要多步推理） |

**不绑定具体产品**：选型时看这几条——是否 **非自回归**（决定确定性和成本）、是否**只算 input**、是否**支持 score 原语**（不是二分类）、是否**能本地跑**（决定可复现）、license。

**部署建议**：本地实现作默认 + 云端实现作增强。两者同属一个品类、两个档次，天然构成 A/B。

## 5. ★ 决策模型不替你做特征工程（真正的工作量在这里）

决策模型吃的是你喂给它的状态。**这是你项目 40% 的工作量，而且不会因为换模型而消失。**

| 维度 | 在问什么 | 你需要先产出什么 | 零依赖的默认做法 |
|---|---|---|---|
| 相关度 | 和活跃 goal / 近期上下文有多近 | 活跃 goal 表 + 候选来源 | **让决策模型在上下文里直接判断**（不必预先算向量） |
| 时效性 | 现在说还有用吗 | 候选生成时就要带 `expires_at` | 纯比较 |
| 新颖性 | 是不是已经知道/说过了 | 已说过记录 | **结构化 dedup key**（同线程/同 URL/同 goal/文本 hash）；语义去重是可选优化 |
| 可行动性 | 我能直接做完，还是只能提醒 | 工具能力清单 | 静态表 |
| **打断代价** | 用户此刻愿意被打断吗 | **勿扰时段 / 最近打扰频率** ← 验证阶段用前者代理；在线状态要等 L4 有即时渠道 | 时间规则 |

> ⚠️ **不要把「特征」理解成「必须预先计算的向量」。** 如果决策层本来就是一次模型调用，**模型能从原始上下文判断相关性和新颖性**——embedding 是可选优化，不是地基。
>
> **依赖顺序**：最后一行意味着 **L4 的在线状态是 L2 的前置**。但邮箱投递给不了在线状态，所以**验证阶段用「勿扰时段」代理，不阻塞**（见 [delivery-layer.md §8](delivery-layer.md)）。

## 6. ⚠️ 陷阱：二分类 + 选择性偏差

**不要做成二分类（推/不推）。** 两个原因：

1. **粒度不够**——需要四档，而且「价值」是连续的。
2. **选择性偏差（更致命）**——训练分类器需要标签，而：

| 标签来源 | 问题 |
|---|---|
| 用户反馈（忽略/点开） | **只有推了才有反馈，没推的没有反馈** |
| 人工标注 | 样本少、成本高 |
| 模型打标 | 那就是在用模型 |

**后果**：模型会学会「少说」（少说就没有负反馈），最后退化成什么都不说——**它学不到「漏报的代价」**。

→ 这是 **bandit / off-policy** 问题，不是标准监督学习。**要修它，唯一的手段是 §8 的审计日志。**

## 7. 硬规则与判断的分工

成熟系统是**混合的**，且要清楚何时用哪种：

| 用**规则**（先判、不打分） | 用**判断**（打分） |
|---|---|
| 后果严重——付款、删除、发邮件 | 后果可逆——提醒、建议、信息 |
| 用明确的偏好表达过 | 用户没有明确说，需要权衡 |
| 确定性高，`if X then Y` 成立 | 模糊，多条信号要权衡 |
| 合规 / 安全要求 | 体验优化 |

**决策顺序**（借 nanoMuse Sentinel 的形状，它在审批层做得最成熟）：

```
候选进来
  ├─ 命中「安全类」 → 一律升级人工确认，不打分
  ├─ 命中「闸门」   → 一律不打扰
  ├─ 命中「用户规则」→ 按规则直接投递（如用户配的页面监控）
  └─ 其余 ← 这才是打分 + 全局预算 + 分档        ★ 价值所在
```

**第 4 条分支才是重点**——因为用户规则只能覆盖用户**想到要配**的东西，而真实生活里绝大多数值得说的时刻，用户事先想不到配规则。

> **规则覆盖不了未知，判断才能。**

### 全局注意力预算

**预算必须跨所有来源共享**（邮件、日历、coding agent 完成通知、goal 巡检同一份额度）。

这是「限频」和「调度」的本质区别：限频是每个来源各自 30 秒最小间隔（如 OpenClaw 的 Heartbeat guard），**没有全局视角**。

## 8. ★ 可解释的沉默（全行业空白，也是本项目的核心）

**所有产品的审计都在记「我说了什么」，没有一个记「我为什么没说」。**

每次裁决必须落库：

```
DecisionRecord {
  decision_id
  candidate        ← 包括**被压下的**候选
  tier
  score
  reasons[]
  basis            ← 规则 / 启发式 / 模型(版本)
  suppressed_by    ← 被预算挤掉？被去重合并？低于阈值？
  created_at
}
```

**它能回答**：「你昨天为什么没告诉我这件事？」

**它同时解决三个问题**：
1. 产品卖点——把判断权交给 agent 的**合法性来源**
2. 调试手段——你能看出策略是不是太保守/太激进
3. **未来训练数据的唯一合法来源**——它记录了「没说」的候选和原因，部分修掉 §6 的选择性偏差

> 没有这一层，agent 的判断就是黑盒，会重演 Muse 的信任崩塌（Muse 崩的不是自动化，是**不透明**）。

## 9. 评测：需要「标签」，不需要「第二套实现」

决策模型的确定性（非自回归）已经解决了 CI 回归。但要回答「打断精确率是多少」，还需要**判据**：

| 判据来源 | 说明 |
|---|---|
| **模拟用户画像** | PROACTIVITY-GYM 的做法：persona-conditioned simulated users |
| 人工标注小样本 | 成本高但可靠 |
| 真实反馈 | **有选择性偏差**，只能作为补充 |

**指标**（借 TRACE 的拆分方式）：

| 指标 | 定义 |
|---|---|
| Interruption Precision | 开口了的里面多少真有价值 |
| Recall of Important Events | 真正重要的有多少被说了 |
| **False-silence rate** | **该说没说的比例**（最容易被忽略、也最伤） |
| Interruptions / day | 每天打断次数 |
| Budget adherence | 预算超支次数 |
| Time-to-signal | 事件发生到开口的延迟 |
| Trust proxy | 忽略率 / 静音率 |
| Dedup correctness | 重复上报被正确合并的比例 |

**评测要能接进 CI 并做确定性断言**——不只是出指标表，而是「改了权重后，precision 不得下降超过 X」。这才叫 harness。

## 10. MVP 建议

```
Step 1  先做特征：在线状态（L4）、expires_at、已说过记录、工具能力表
        ← 这步不做，任何模型都是空转
Step 2  用规则 + 启发式打分跑通「候选 → 四档」全链路
        权重写成显式常量
Step 3  接决策模型作为 ModelPolicy（接口同构，可开关）
Step 4  加审计：decision_id + reasons[] + 被压下的候选
Step 5  加回放评测 + CI 断言
Step 6  有 200–500 条带判据的裁决记录后，再做 A/B（规则 vs 启发式 vs 模型）
```

**Step 3 不是第一步**——因为决策模型解决的是「判断」，「特征」和「出口」都没做好时，换模型没有任何可观测收益。
